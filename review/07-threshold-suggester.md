# 07 - Threshold suggester

**Verdict: REWORK (2/10).** It optimises a number nobody sees, and its forward-looking accuracy is worse than "use yesterday's value".

## What I ran
- Read `threshold-suggester/index.js`, `test.js`, README, and `app/core.js` (`TEMPLATES`, `fromTemplate`, `open`, `newMarket`).
- `repro/07-edge.js` (input handling, p0 check), `repro/07-fuzz.js` (200k random inputs), `repro/07-backtest.js` (forward simulation, 7 models, windows 7 and 30, 3000 histories x 300 next-day draws each), plus CLI invocations.

## Findings

| ID | Sev | Finding | Evidence | Fix |
|---|---|---|---|---|
| F1 | **Critical** | **The tool's "chance" is NOT what players see.** `fromTemplate` hardcodes `p0: 0.5`; the `open` action ignores threshold for the opening price. Every daily market opens at 50% whatever x is. The threshold only defines the question. README ("so it opens between 30% and 70%"), the header comment and the CLI output ("about 57%") are wrong about the product. CONFIRMED | core.js:153 `closesOn: close, closeCity: 'uk', p0: 0.5`; `07-edge.js` seeds q1/q2/q3 and prints `hist[0][1] = 0.5` for all three. | Reword README/CLI to "pick a threshold the next reading is a coin flip around". Optionally let `open` take a `p` and use `p0 = suggester chance` (create already supports `a.p`). Otherwise the stated goal is moot. |
| F2 | **High** | **Statistically it is the wrong estimator.** It uses the share of past values above T (a climatology), ignoring order, trend and autocorrelation. Forward test, true P(next day > T) minus 50%, averaged (suggester vs naive "T = yesterday's value"): taka crawl W=7: 37.1pp vs 12.2pp; W=30: 47.3pp vs 12.1pp. GBP W=7: 28.4pp vs 2.3pp; W=30: 38.8 vs 2.3. LHR autumn W=30: 33.6 vs 17.4. Share of suggestions whose true P(YES) falls outside 20-80%: taka crawl W=30: 94% vs 0%; GBP W=30: 75% vs 0%. True P(YES) lands inside the claimed 30-70% band only 3% (taka W=30), 17% (GBP W=30), 20% (LHR autumn W=30). Drifting taka (+0.15/d): 0% in band for both rules (any history-based rule fails). Only a stationary series (Dubai W=7) is on par (20.5 vs 21.1pp). CONFIRMED on my simulated models (assumed parameters; real data not tested) | `node repro/07-backtest.js` | For slow-moving series (taka, GBP) use the latest published value (rounded to the data precision), or last value plus recent drift. For temperature use a same-calendar-week climatology (previous years) or last value +/- seasonal slope. Drop the window-share logic. |
| F3 | High | **The 30-70% guarantee only holds in-sample.** 200k random histories: 0 violations of the band on the history, 0 print mismatches. That is true by construction, because the threshold is selected on the very data it is scored on. It says nothing about the next day (F2). The CLI also does not warn. CONFIRMED | `07-fuzz.js`: `bandViolations: 0` | Say "of the last N days", never "opens at". |
| F4 | High | **Wrong sign handling / unusable values vs core.** core accepts only `/^\d+(\.\d+)?$/` for x (core.js:149). The tool can output `-3`-style thresholds (negatives from "below -3" data), `3e+21`, `1e-7` and the like, all of which `open` rejects with `bad_threshold`. Current templates (London max in winter, Q2) can go to 0 or below. CONFIRMED | `07-edge.js` last two lines: `/^\d+(\.\d+)?$/` fails on -2, -0.5, 1e-7; `String(3e21)` is `3e+21` | Either core allows a leading `-` and the tool refuses to print exponent form, or the tool says so. Output via `toFixed(d)` not `Number()`. |
| F5 | Medium | **Tie semantics do not match templates.** `chance()` uses strict `v > t` / `v < t`. Q5 reads "reach {x} F" (>=); Q1 "weaker than", Q2/Q3/Q6 "above" are strict. Integer-reading temperatures tie a lot: simulated P(next == T) is 10-25% for integer Tmax at the suggested T (LHR 0dp W=7 12.8%, Dubai W=7 24.4%, W=30 20.2%), so a tie-resolving mismatch moves the true probability by that much. The tool has no per-template tie rule. CONFIRMED (code + simulation) | index.js `chance`; `07-backtest.js` tie column | Take the template id; treat Q5 as `>=`; prefer thresholds that cannot tie (e.g. .5 above for integer data, but see F6). |
| F6 | Medium | **Precision.** Decimals come from `String(v)` split on '.', so `1e-7` gives 0 decimals (series of tiny numbers throws "too flat"), mixed 2 and 1 decimal inputs give e.g. 122.55 from 122.1/122.45 mix. Midpoint candidates are rounded to the data's decimals, so `[10..15]` outputs 12 (an observed value that can tie) while real readings only come in integers: if the reading equals T the question resolves NO for "above", the tool's own 50% hides a 15-25% tie mass. 33,581 of 188,777 fuzz suggestions were not an observed value (midpoints), not harmful but unexplained to the admin. CONFIRMED | `07-edge.js`, `07-fuzz.js` | Offer .5 steps for integer-valued data, round to the template's published precision (BB 2dp, BoE 4dp, Met Office 0.1). |
| F7 | Medium | **Silent coercion of garbage input.** `Number('')`=0, `Number(null)`=0, `[]`=0, `true`=1, `'0x10'`=16, `'1e3'`=1000 all accepted as data; NaN/Infinity strings silently dropped (a 7-value paste with 2 typos becomes n=5 with no warning). `dir` of anything other than `'below'` ('abov', 'BELOW', 'up') silently becomes 'above'; CLI echoes the typo ("up it: about 50%"). CONFIRMED | `07-edge.js`: `[''x6,'1','2','3']` returns threshold 0, chance 33; `s(base,'abov')` returns above result; `node index.js up 1 2 3 4 5 6` | Reject non-numeric tokens (`/^-?\d+(\.\d+)?$/`), reject unknown dir, error if any token dropped. |
| F8 | Medium | **CLI argument parsing.** First arg is always `dir`: `node index.js -3 -1 0 2 1 4 0` treats `-3` as direction, silently runs as "above" on 6 values, prints "(-3 it: about 50%...)", exit 0. `--help` gives "need at least 5 recent values". Comma-separated paste (`1,2,3,4,5,6`) fails the same way. CONFIRMED | CLI runs above | Validate dir first, add `--help`, accept commas. |
| F9 | Low | Robustness: `Math.max(...vals.map(...))` throws `RangeError: Maximum call stack size exceeded` at 200k values; O(n^2) candidate scan otherwise OK (20k values in 60 ms). `-0` input renders fine. Flat/mostly-flat series (e.g. `[5x8, 6, 6]`) throw "too flat" although a coin-flip threshold exists via the "reach" direction; 11% of random histories throw. CONFIRMED | `07-edge.js` | Loop for max; fall back to lo/hi widening. |
| F10 | Low | Tests only assert in-sample membership of the band on 3 tiny inputs; no test for the claim in F1/F2, ties, strings, negatives, CLI. Order of the "oldest first" values is ignored (values are sorted), so the documented ordering is meaningless. CONFIRMED | `test.js` | Add forward-backtest test and CLI tests. |

## What actually holds up
- In-sample the band guarantee is exact (200k fuzz, 0 violations, printed percent always equals the true in-sample share).
- Unit tests pass; 20k values runs in 60 ms; flat series produce a clear error rather than a nonsense threshold.
- Stationary, low-drift data (Dubai Tmax, W=7) is no worse than the naive rule.

## Does this item matter?
Not as built. The player-visible starting price is always 50% regardless of the threshold, so the "opens at 30-70%" promise is empty, and the real goal (a fair, uncertain question) is met better by the trivial rule "yesterday's published value" (2-12pp off 50% vs 28-47pp for this tool on taka and GBP). For a 10,000-player play-money game an admin typing yesterday's rate into the threshold box is both simpler and more accurate. Only worth keeping if reduced to a rounding/formatting helper that checks core's number format and per-template tie rule.
