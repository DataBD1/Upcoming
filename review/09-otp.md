# 09 — Phone OTP (lib/sms.js, otpSendCheck/otpVerify, otpsend/otpverify, "Log in with an SMS code")

## Verdict: FIX FIRST — 4/10

OTP as shipped is not safe to turn on (`OTP_ENABLED=1`) without at least the IP-trust and
password-bypass fixes below. With it off (the base case in business/finance.md) this code is dead
and harmless, which is the only reason it isn't KILL.

## What I ran
- `node repro/09-enum-oracles.js`, `09-bruteforce-and-hash.js`, `09-admin-simswap.js`,
  `09-pumping-cost-and-ipcap.js`, `09-webhook-ssrf-leak-timing.js` against `lib/handler.js` +
  `lib/filestore.js` directly (in-process).
- `sh repro/09-xff-spoof.sh` against a real `server.js` on `PORT=8109` with `curl`.
- `repro/09-pg-otp-concurrency.js` against two instances of `api/index.js` on a real embedded
  Postgres (port 54409), via the sandboxed non-root `setpriv` pattern from BRIEF.md.
- Read `business/finance.md` for the SMS rates (UK 0.056, US 0.012, UAE 0.1176 USD/segment) and
  `OTP_DAILY_CAP` default (200).

## Findings

| ID | Severity | Finding | Evidence | Proposed fix |
|---|---|---|---|---|
| F1 | Critical | **OTP login fully bypasses the password, for every account including admin.** `otpVerify` signs in on the code alone; there is no PIN check anywhere in the OTP path. Whoever controls the phone number (SIM swap, port-out, carrier social engineering, SS7) gets the account, admin included. | `repro/09-admin-simswap.js`: admin signs up with a PIN, then logs in via OTP with **no PIN given at all** and gets `me.admin === true`. CONFIRMED. | `lib/handler.js` `otpVerify`: do not allow OTP login into an account flagged `admin` (require password reset by another admin instead, or a second factor), or at minimum log/alert on OTP logins to admin accounts and force a short session + re-auth for admin actions. |
| F2 | Critical | **Per-IP otpsend cap (10/hr) is fully bypassable.** `lib/handler.js:289` takes `ip = (x-forwarded-for).split(',')[0]`, i.e. the *first*, client-supplied hop — not the hop a proxy appends. Even behind a real reverse proxy (Vercel appends the true client IP; it does not strip a forged leading entry), the first value is attacker-controlled. Locally this is directly exploitable with no proxy at all. | `sh repro/09-xff-spoof.sh`: one real client, 12 different spoofed first-hop IPs (each with a fixed "trusted" tail IP appended), all 12 `otpsend` calls succeed — the 10/hr per-IP cap never engages. CONFIRMED. | `lib/handler.js`/`server.js`: take the **last** XFF entry (or `req.socket.remoteAddress` only, with Vercel's proxy as the sole trusted hop) instead of `[0]`; or drop the per-IP cap entirely and rely on the per-number cap + a global daily cap with alerting, since IP is unauthenticated input end to end. |
| F3 | High | **SMS pumping / toll fraud: sign-up has no verification, so an attacker registers accounts on numbers they own and pulls OTPs.** The per-number cap (3/hr = 72/day) and the global `OTP_DAILY_CAP` (default 200) are the only real limiters, and 3 attacker numbers alone exhaust the whole day's global cap (a DoS on every legitimate OTP login), while costing the operator real money to numbers the attacker may be paid on. | `node repro/09-pumping-cost-and-ipcap.js`: 40 unverified UAE-style sign-ups, no IP reuse; blocked only once the per-number 3/hr limit bit, never the per-IP limit; `ceil(200/72)=3` numbers exhaust `OTP_DAILY_CAP`; at finance.md's quoted rates, an attacker who always triggers the full daily cap to UAE costs **$23.52/day ($705.60/30 days)**, UK $11.20/day ($336/30d), US $2.40/day ($72/30d). CONFIRMED (cost math), CONFIRMED (cap exhaustion by 3 numbers). | Require signup to not be the gate at all for *abuse* — instead cap OTP sends per-account-age (e.g. no OTP login allowed within N minutes of signup) and alert/kill-switch when the daily cap is hit instead of silently capping; consider a lower, phone-number-verified-at-signup requirement before OTP login is offered for that number, since signup itself takes no verified contact today. |
| F4 | High | **Account enumeration via `otpsend`: three independent oracles**, despite the "same reply for unknown numbers" comment. (1) Timing: a known number does a `transact()` write + real HTTP SMS send (hundreds of ms with a slow provider); an unknown number returns in ~0ms. (2) The 4th+ request: a known number eventually returns `400 slow_down`, an unknown number returns `200 ok` forever (no cap ever applies to it). (3) If the SMS provider is down/erroring, a known number gets `400 otp_send_failed`, unknown always gets `200 ok`. | `node repro/09-enum-oracles.js`: known ~410-480ms vs unknown ~0-1ms; known hits `slow_down` after 3 sends, unknown never does; provider-down known → `otp_send_failed`, unknown → `ok`. CONFIRMED, three separate oracles, no timing even needed for (2)/(3). | Make `otpSendCheck` do equivalent work (a dummy scrypt-weight op, or at least an equivalent read+conditional no-op write) and equivalent latency for the unknown-number branch, and apply the IP/day caps to unknown-number requests too so they also eventually rate-limit identically. |
| F5 | Medium | **Code hash is cheap to crack if the DB leaks.** `sha256('otpcode:'+phone+':'+code)` over a 1e6-value space, unsalted beyond the phone number, no work factor. A single core recovers a specific stored code from its hash in well under a second. | `node repro/09-bruteforce-and-hash.js`: offline crack of a real stored hash found the code in 568ms, single core, no parallelism attempted. CONFIRMED. The *online* 5-try/code gate makes live guessing impractical (≈0.036%/day by the math in that script), so this only matters on a DB leak, where the attacker already has bigger problems — but it's a free win to use HMAC with a server secret instead of a bare hash, costing nothing. | `lib/handler.js` `otpSendCheck`/`otpVerify`: HMAC-SHA256 with a server-side secret (e.g. reuse the admin-reset pattern) instead of a bare `sha256(phone:code)`, so a DB-only leak doesn't hand out crackable codes. |
| F6 | Medium | **Webhook provider: failed/slow send still consumes a send-attempt and leaves a valid code sitting in state**, because `otpSendCheck` issues+stores the code and burns the rate-limit slot inside the Postgres/file transaction, then `Sms.send()` is awaited afterward. A slow provider (tested at 1.5s) also makes `otpsend` hang the HTTP response for that long with no user-facing feedback besides eventual failure. | `node repro/09-webhook-ssrf-leak-timing.js`: part (b) — a failing+1.5s-slow webhook: client gets `otp_send_failed` after 1.5s, but the code record in state is still present and valid (`tries:0`) — if that SMS was in fact delivered by the gateway despite the HTTP response to the app failing (webhook timeout, not an actual non-delivery), the code is usable, but it was already counted against the 3/hr cap for nothing. | Only commit the code to a "live" state in a *second* step after `Sms.send()` succeeds (store a pending record first with a short pre-OK TTL, or roll back the send-count on failure, matching the comment's own intent that a flood "cannot run up the SMS bill" — a failing provider shouldn't burn budget either). |
| F7 | Low | **https:// is correctly enforced** for `SMS_WEBHOOK_URL` (`available()` regex), so classic SSRF-via-scheme is blocked, and **no webhook URL/token is leaked** to the API caller on failure (`otp_send_failed` only). CONFIRMED good. | `node repro/09-webhook-ssrf-leak-timing.js` parts (a) and (c). | None needed; note that `SMS_WEBHOOK_URL` is still operator-controlled env, not attacker input, so classic SSRF isn't really in scope here — the real risk is F6/F3, not URL injection. |
| F8 | Low | **Console provider logs the phone number and the OTP code in plaintext to stdout**, and the SMS body has no app name ("Your code: 123456 (valid 5 minutes)"), which both leaks into any log aggregation and makes the message indistinguishable from a phishing text. | `node repro/09-webhook-ssrf-leak-timing.js` part (d): stdout line contains the raw phone and raw code; `message names the app: false`. CONFIRMED. (Console provider is documented "local testing only; refused in production", so production impact needs a leaking webhook relay, not this provider — lower severity.) | `lib/sms.js`: prefix the SMS text with the app name ("DHK Predicts: your code is…") regardless of provider; for `console`, consider masking the code in the log line it's meant to stand in for a real send. |
| F9 | Low | **No double-submit guard on the OTP form.** Unlike `buy`/`sell` (`el.disabled = true` before the API call), `public/app.js`'s `otpform` submit handler never disables the button, so a double-tap sends two `otpsend`/`otpverify` calls, burning extra budget against the 3/hr-per-number cap. | Read `public/app.js` lines ~746-751 (buy/sell disable) vs ~789-796 (otpform, no disable) — grep for `disabled` shows no hit near the OTP handler. SUSPECTED at UI-interaction level (not driven with Playwright), CONFIRMED at code level (no guard exists). | `public/app.js`: disable the OTP submit button on click, same pattern as `buy`. |

## What actually holds up
- **Postgres concurrency** (`repro/09-pg-otp-concurrency.js`, real embedded Postgres, two instances): a code sent on instance A verifies correctly on instance B; 10 concurrent wrong-code verifies split across both instances all correctly fail, and the code is unusable afterward — no double-budget or lost-update bug found. One caveat: `otp` is not in pgstore's `SHARDED` list, so it lives in the single un-sharded main blob row — every unrelated write in the app touches/versions that row, a potential hot-row bottleneck under load, not a correctness bug (not load-tested here).
- https-only enforcement on the webhook URL, and no secret leakage on provider error (F7).
- The *online* brute-force gate (5 tries/code) is mathematically fine on its own (~0.036%/day); the problem is everything feeding into it (F2-F4), not the gate itself.

## Does this item matter?
For a 10,000-player play-money game with no real money, a full password bypass reachable by SIM-swapping an admin's number (F1) and a trivially-bypassable rate limiter (F2) are not "SMS OTP scaffold" nitpicks — they're exactly the kind of thing that turns a side feature into the easiest way to take over the whole admin panel or run up a sponsor-funded SMS bill, both of which are called out as live risks in business/finance.md itself ("SMS pumping fraud is UNKNOWN but real; it needs rate limits plus a hard provider cap"). Given the base case in finance.md keeps OTP *off* at launch, shipping the code gated behind `OTP_ENABLED=1` is fine as a scaffold, but it is not close to safe to flip on in production yet, and F1+F2 should block that switch regardless of any further feature work on it.
