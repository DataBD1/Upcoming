# Review 10: scaling work (pgstore cache, backup, bench, docs/scaling.md)

**Verdict: REWORK (3/10).** The cache has a data-losing race (CONFIRMED), a process-crash bug on any lost DB connection, and several unbounded-growth cliffs. All of docs/scaling.md's headline numbers were measured on localhost with the cache never under concurrent same-instance read/write pressure.

## What I ran
Harness `repro/10-lib.js` (embedded PG on 54410, optional per-round-trip latency, `LAT` ms +0..100% jitter). Scripts in `/home/user/upcoming/review/repro/10-*.js`. Run as nobody: `export TMPDIR=/tmp/pgrun; setpriv --reuid=65534 --regid=65534 --clear-groups env HOME=/tmp/pgrun TMPDIR=/tmp/pgrun PATH=$PATH node 10-xxx.js`.
Fuzz `10-fuzz.js <steps> <seed> <concurrency>` (3 store copies, ~20 real API actions, clock skew, compares every copy and the DB after every step). Serial: 8 seeds, 0 divergence (VERIFY on and off). Concurrent with `LAT=4`: divergence in 2 of 7 completed runs. Soak: `10-soak.js <players> <req/s> <s> <copies>` (adapted bench/soak.js plus latency plus end-of-run cache-vs-DB check). Seeds: `10-pghold.js`, `10-seed.js`, `10-heavy-seed.js`. Measurements: `10-mem.js`, `10-ops.js`, `10-snapshot.js`, `10-herd.js`, `10-mainrow.js`, `10-backup.js`, `10-pool.js`. The box has 4 cores shared with other reviewers, so timings are noisy.
Not run: `npm test`, `test-pg.js`, live Vercel Blob/Supabase.
Self-incident: early on I ran `pkill -u 65534 postgres`, which could have killed another reviewer's embedded Postgres if it shared my process namespace (`ps` showed none afterwards). Sorry.

## Findings
| ID | Sev | Finding | Evidence | Fix |
|---|---|---|---|---|
| F1 | **Critical** CONFIRMED | `read()` refresh and `transact()` on the SAME instance interleave. The read applies delta rows from an OLDER snapshot over keys the write already changed in memory, and resets `cache.version`. Cache silently differs from DB; the next write touching that key writes the stale value back. Player got 30 points back and the position vanished. `PGSTORE_VERIFY=1` does not catch it. | `repro/10-race-readrefresh.js` (deterministic gate). Output: `DB pts 940 / cache pts 970`, then `after one more buy DB pts 965 (expected 935) ... LOST UPDATE`. Fuzz: `LAT=4 node 10-fuzz.js 120 2 6` and seed 3 print FIRST DIVERGENCE (a position present in DB, missing in cache). | pgstore.js: one in-process async mutex around every cache mutation (sync, transact, refresh). In `sync()` ignore a snapshot older than `cache.version` (`if (row.version <= cache.version) return`). Never lower `cache.version`. |
| F2 | **High** CONFIRMED | `pool.connect()` clients have no `'error'` listener. Any lost connection (pooler restart, idle-in-txn timeout, `pg_terminate_backend`) while a client is checked out is an unhandled `'error'` event, so the Node process exits. Same in api/backup.js. | `node 10-crash-dirty.js` -> `Unhandled 'error' event ... ECONNRESET`, exit 1; also with the query in flight (`MODE=inflight`). | `c.on('error', () => {})` right after `pool.connect()` in read/transact/backup, or `pool.on('connect', cl => cl.on('error', ...))`. |
| F3 | **High** CONFIRMED | Main row is not "small": `markets[].book` and `.paid` keep one entry per holder forever (62 B/holder/market) and the whole row is rewritten by every write. 3,000 holders: 100 resolved markets = 21.7 MB, a trivial write takes 1.8 s (local). At 3 markets/day that is ~month 1. docs say "a few hundred KB, shard at 1 MB". | `node 10-mainrow.js 3000`: 10 mkts 2.4 MB / 156 ms, 30 mkts 6.7 MB / 425 ms, 100 mkts 21.7 MB / 1841 ms. | Move book/paid to a shard coll keyed by market, or drop them after the 48 h dispute window. Same for `seen`. |
| F4 | **High** CONFIRMED | With real DB latency the store falls over at far lower load than docs claim. A write is ~9 round trips under ONE global row lock, and writers hold pool connections (max 5) while waiting for it, so reads queue behind writers too. Collapse, not degradation. | `LAT=10` (avg 15 ms/trip): 60 req/s -> p50 1.3 s, p95 7 s, achieved 48/s; 200 req/s -> p50 46 s, achieved 46/s. `LAT=2`: 100/s fine (buy p95 164 ms), 200/s -> p50 3 s. `LAT=5`: 60/s ok (buy p95 270 ms). No 5xx, just unbounded queues. 100 concurrent buys on one copy: 51 writes/s (docs: ~150), a read during it waited 1.8 s. | Separate read pool; collapse write round trips into one statement/function; `connectionTimeoutMillis` plus 429 when the queue is long; document RTT-based ceiling (~1/(9*RTT) writes/s). |
| F5 | **High** CONFIRMED | `app_state_history` is never pruned (grep: no DELETE). Each snapshot is the full state: 0.7 MB at 10k players (light), 5.9 MB at 100k, 7.7 MB at a "heavy" 10k. Up to 144/day: ~95 MB/day at 10k light. | `node 10-snapshot.js n10000/n100000/h10000` prints stored size. | housekeeping(): keep N recent plus 1/day, delete the rest. |
| F6 | **High** CONFIRMED | The 10-minute snapshot runs `JSON.stringify` of the whole state on the event loop and inserts it under the global lock. | `10-snapshot.js`: no-op write 20 ms vs 312 ms @10k light; 2.3 s @100k (575 ms stall); **11.7 s @ heavy 10k** (107 MB state: 5,000 traders x 200-entry log x 30 positions; stall 1.2 s). Vercel function limits make that a timeout. | Take the copy in SQL (`insert ... select` from shards) off the request path, or rely on a daily dump/PITR. |
| F7 | **High** CONFIRMED | `cache = null` while requests are in flight: a read or write that passed the `if (cache ...)` check resumes and dereferences null -> TypeError -> HTTP 500 / failed write. Happens at every TTL reload and after any failed write. Also seen in the fuzz. | `10-race-ttl-500.js`: `(a)` read 500, `(b)` write 500 (`reading 'version'`, `reading 'state'`). | Build a new cache object and swap it; use a local `const c = cache`. |
| F8 | Medium CONFIRMED | Restore/migration hard-deletes shard rows (no tombstone), so an instance idle through it keeps removed players ("ghosts"): their session still works, login recreates an orphan session row. A version that goes DOWN (`row.version < cache.version`) is never reloaded. | `10-restore-ghost.js`: `C session of player 2 still valid: 200` vs 401 on B; `2 session rows vs 1 expected`; `C sees changed row? false`. | Reload fully when `row.version < cache.version` or when a legacy row was seen; tombstone in `saveFull`. |
| F9 | Medium CONFIRMED | Postgres errors carry `.code`, so handler.js (`e.code ? 400`) returns DB failures as HTTP 400 and never logs them. `\u0000` in any text (guest `feedback`) is legal JSON but jsonb rejects it: 400 `22P05`, and each one drops the cache -> full reload (5 poison + 5 reads = 6 reloads; ~1.2 s each at 100k). Cheap unauthenticated DoS. | `10-crash-dirty.js` prints `400 {"error":"57P01"}`, `400 {"error":"22P05"}`, `6 full state reloads`. | handler.js: treat non-app codes as 500 + log. Strip NUL in core.js inputs. On a DB write error roll back the delta instead of dropping the whole cache. |
| F10 | Medium CONFIRMED | Dirty reads: readers on the same instance see an uncommitted write (pts 900) that is later killed (pts back to 1000). | `10-crash-dirty.js` line (1). | Mutate a copy, publish after commit. |
| F11 | Medium CONFIRMED | Every cold start runs `alter table ... add column if not exists` (ACCESS EXCLUSIVE even when it exists). It waits behind any open transaction and blocks all other queries on `app_shards` meanwhile. | `10-init-lock.js`: ordinary SELECT blocked 2507 ms. | Check `information_schema` first, or run DDL at deploy only; `lock_timeout`. |
| F12 | Medium CONFIRMED (latent) | Reads call `Core.migrate` on shared cached shards with touch-tracking off: change is cached but never saved, and `state.v` bumps so the write path skips the migration. | `10-read-migrate.js`: DB auth key stays `01712345678`, main `v:4`, fresh copy login -> `wrong_login`. Only affects sharded DBs below v3; any future migration touching a shard hits this. | Run migrations only inside `transact`. |
| F13 | Medium CONFIRMED | `/api/backup` is public unless `CRON_SECRET` is set (rewrite excludes it, middleware exempts it) and loads+stringifies the entire state before checking whether today's blob exists. 5 MB/0.25 s @10k; 40 MB/1.8 s/peak RSS 442 MB @100k, per anonymous call. `already exists` string match is unverified against the real SDK (not in `@vercel/blob` 2.8.2 source I grepped). | `10-backup.js` (fake blob): calls 2 and 3 `wrote:false` but still 233 ms / 1.8 s. | Fail closed without `CRON_SECRET`; check existence (`head`) first; stream. |

N copies cold-starting together (every deploy) each pull the whole state: 10 copies @100k = 8.2 s each; 30 @10k = 3.5 s. | `10-mem.js`, `10-herd.js`. | Delta-load on cold start from a shared snapshot; stagger TTL with jitter. |

## What holds up (tested)
- Serial fuzz, 8 seeds x 200-400 steps, 3 copies, with and without `PGSTORE_VERIFY=1`: cache == DB at every step.
- Two cold copies racing the first write on a legacy row plus a concurrent reader: no lost write, one migration (`10-legacy-race.js`).
- Weekly `s.weekstart = {}` replacement and refused-request rollback work (fuzz plus soak end-of-run check: 0 differing keys in 8 soak runs).
- Kill of a backend before commit leaves the DB unchanged (with F2 fixed).
- docs "tens of MB at 10k" and "150 ms to 1 s cold start" are true for the light benchmark state only.

## Docs claims the evidence does not support
"200 req/s" (localhost only); "writes about 150/s" (51/s here); "Main row 18 KB / shard at 1 MB" (F3); "Memory: not measured" (now measured, F14); `docs/operations.md` says backup restore is just "load the JSON" (no version bump, no ghost warning).

## Does this item matter?
Yes, it is the heart of the hosting plan, but a play-money game with ~3,000 daily players and 10-20 req/s does not need a hand-rolled cache with delta sync. The measured cost is a rewrite of the store invariants (F1) plus three unbounded tables (F3, F5, events) that bite within weeks. A plain "read from Postgres per request" with indexed per-row reads would handle 10-20 req/s at 2-5 ms RTT without any of F1, F7, F8, F10, F12.
