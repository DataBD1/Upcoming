# 02 size-budget review

**Verdict: FIX FIRST, 5/10.** The tool works on the happy path and its own test passes, but it measures a number no user downloads, counts a file that is never shipped, and silently accepts malformed config.

## What I ran
- `node ../../size-budget/index.js size-budget.json` in app/ (rc=0, total 44.8 / 46 KB), plus `node size-budget/test.js` (passes).
- Playwright first load against `PORT=8102 node server.js`: `review/repro/02-measure.js` (CDP wire bytes + brotli q11/q5/q4 + gzip sweep) and `review/repro/02-sw-precache.js` (includes service-worker requests).
- 17 edge cases for the tool: `review/repro/02-tool-bugs.sh`.

## Findings

| F1 | High | **Budget is measured at brotli q11, which real CDNs do not use.** On Vercel the edge compresses static files itself (lower brotli quality; I could not test Vercel, SUSPECTED for exact numbers). The check says "ok" for sizes that would FAIL under realistic compression. The local server (`server.js` line 20) also uses q11 default, so even the local Playwright measurement is flattering. | `02-measure.js` table: app.js 112005 raw, br11 25.2, br5 28.1, br4 30.9, gz9 29.4. CONFIRMED for the numbers; CDN behaviour SUSPECTED. | `size-budget/index.js`: measure with q5 (or report both q11 and gzip9) and set budgets from that. Or state in README that budgets are "best case". |

## What holds up (tested)
- Over-budget detection per file and total, rc=1, negative and null budgets fail; total 0 fails; unicode paths, symlinks, config in another directory (paths relative to the config file) all work; `excludeFromTotal` works.
- A 300 MB zero file brotli-compressed fine (no input-limit problem at q11 for this size; I did not test above that).
- The q11 numbers match what Chromium actually received from the local server (app.js 25842 B on the wire vs 25.2 KB measured), so the tool is accurate for what it measures.
- core.js is correctly measured from the repo root, which matches what `vercel.json` copies into public/.

## Does this item matter?
Marginally. For a 10,000-player play-money game on mobile data in Bangladesh, bundle size is a real concern, and a CI guard on it is a reasonable cheap idea. But as built it guards a number that is neither the shipped bytes (wrong compression, wrong file set) nor tight enough to reflect a regression. The fixes are small (drop social.js, measure at q5, derive files from sw.js, validate config) and would make it honest. As is, it gives false comfort.
